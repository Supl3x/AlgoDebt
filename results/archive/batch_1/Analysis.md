# LLM Evaluation Analysis

## Overview
This document compares the performance of various Large Language Models (LLMs) against our baseline rule-based AST detector for identifying Algorithm Debt in Machine Learning code. The baseline Ground Truth was generated by parsing the Python Abstract Syntax Trees (AST) of real-world ML repositories.

## 1. Gemini 3.5 Flash
**Total Token Usage:** ~295,855 tokens

| Anti-pattern | Precision | Recall | F1 Score | TP | FP | FN | TN |
|---|---|---|---|---|---|---|---|
| hardcoded_hyperparameters | 0.86 | 0.14 | 0.24 | 12 | 2 | 73 | 113 |
| missing_data_validation | 0.71 | 0.83 | 0.77 | 5 | 2 | 1 | 192 |
| train_test_leakage | 0.75 | 1.00 | 0.86 | 3 | 1 | 0 | 196 |
| no_reproducibility_control | 0.47 | 0.24 | 0.32 | 7 | 8 | 22 | 163 |
| silent_exception_handling | 1.00 | 0.35 | 0.52 | 7 | 0 | 13 | 180 |

**Analysis vs. Baseline (Algorithm):**
Gemini 3.5 Flash performed exceptionally well on complex, nuanced patterns like `train_test_leakage` (100% Recall, 75% Precision) and `missing_data_validation` (83% Recall, 71% Precision). It achieved perfect precision (1.00) on `silent_exception_handling`, meaning every single flag it raised was correct, though it missed several (35% Recall). Its major weakness is `hardcoded_hyperparameters`, where it missed 73 instances (14% Recall), suggesting it struggles to reliably scan long files for scattered literal integers or floats.

## 4. Groq (Llama 3.3 70B Versatile)
**Total Files Processed:** 199 files

| Anti-pattern | Precision | Recall | F1 Score | TP | FP | FN | TN |
|---|---|---|---|---|---|---|---|
| hardcoded_hyperparameters | 0.58 | 0.77 | 0.66 | 58 | 42 | 17 | 82 |
| missing_data_validation | 0.03 | 1.00 | 0.07 | 5 | 143 | 0 | 51 |
| train_test_leakage | 0.12 | 0.33 | 0.18 | 1 | 7 | 2 | 189 |
| no_reproducibility_control | 0.17 | 0.92 | 0.28 | 24 | 119 | 2 | 54 |
| silent_exception_handling | 0.67 | 0.43 | 0.52 | 6 | 3 | 8 | 182 |

**Analysis vs. Baseline (Algorithm):**
Llama 3.3 70B (via Groq) demonstrated strong capabilities in identifying syntactically localized anti-patterns, specifically `hardcoded_hyperparameters` (F1: 0.66) and `silent_exception_handling` (F1: 0.52). In these categories, the LLM successfully identified a substantial number of true positives while maintaining reasonable precision.

However, its performance collapsed on broader, file-level structural issues—most notably `missing_data_validation` and `no_reproducibility_control`. While it achieved near-perfect recall (1.00 and 0.92, respectively), it did so by aggressively over-flagging, resulting in abysmal precision (0.03 and 0.17) and an enormous number of false positives (143 and 119). 

This strongly corroborates the paper's core hypothesis: without specific context about a file's "role" (e.g., whether it's an actual training script versus a utility file or model architecture definition), the LLM adopts a coarse heuristic. It flags almost every Python file that imports ML libraries for lacking data validation and seed controls, regardless of whether those checks logically belong in that specific file.

### Key Takeaways

1. **Syntactic vs. Structural Debt:** 
   LLMs like Llama 3.3 70B and Cohere excel at identifying **syntactic debt** (e.g., hardcoded hyperparameters, silent exceptions). They can spot literal values inside `fit(epochs=50)` or `lr=0.01` very well. Conversely, they struggle profoundly with **structural debt** (e.g., missing validation or reproducibility controls). Llama 3.3 flagged 143 files incorrectly for missing data validation because it couldn't deduce that the file wasn't supposed to handle data validation in the first place.
   
2. **The "File-Role" Context Problem:**
   As highlighted by Llama 3.3's massive false positive rate (and Mistral's total breakdown), LLMs over-generalize. If they see `import torch` or `import pandas`, they assume the file is a complete ML pipeline.
   *Example:* If a repo has a `config.py` file or a `download_weights.py` file, the LLM will flag it for "missing reproducibility control" because it has no random seed, completely ignoring that it's just a helper script.

3. **Gemini's Anomaly on Structural Debt:**
   Gemini 3.5 Flash is the notable exception, scoring high on `train_test_leakage` (0.86) and `missing_data_validation` (0.77). It appears to have a more conservative threshold or better internal reasoning about when a file is actually processing a dataset, preventing the massive false-positive explosions seen in Llama 3.3 and Mistral.

### Conclusion for the Research Paper
General-purpose LLMs are not yet ready to act as standalone, drop-in replacements for AST-based rule detectors across all categories of algorithm debt. They are best deployed in a **hybrid pipeline**:
- Use LLMs (like Llama 3.3) for high-recall triage of syntactically localized issues (hardcoded values, exceptions).
- Introduce a pre-processing LLM step ("File Role Classification") to explicitly tell the evaluating LLM whether a file is a training script or a utility script, which would mitigate the massive false positive rates for structural anti-patterns.
